# Carrier class foundation

Pegasus is the testbed, not a separate ruleset. Once a mechanic is proven, promote the implementation to shared carrier-class code and test it on both Pegasus and Bifrost. A future carrier should register a new identity rather than copy a carrier implementation.

- **Class rules:** common actions, eligibility and limits, launch and docking flows, inventory and pilot readiness rules, and Armada strength calculation. Each distinct ship class can define different rules when explicitly intended.
- **Identity:** stable vessel ID, display name, hull and art, admiral and portrait, faction, and optional formation members. An escort attached to one Armada does not become a class feature.
- **State:** independent location, squadron and reserves, pilot availability, resource balances, and battle/repair history. Shared rules are not shared balances; joining with the same class does not merge state.
- **Onboarding a carrier:** register identity, initialize only its own state, enable the common route/actions, and verify both feature parity and isolation of its inventory and losses. Do not copy carrier IDs or save data.

## Ship tiers and command roles

| Tier | Hull classes | Command role and purpose |
| --- | --- | --- |
| Low | Fighter, vessel (including freighters) | Pilot only. These hulls have basic ship features and no captain or admiral role. |
| Mid | Corvette, frigate | Can have a **Captain**. The Resolute is a corvette and can escort an Armada without becoming its flagship. |
| High | Cruiser, carrier | Can have an **Admiral** and serve as the guild's flagship, leading the Armada and giving missions through its admiral. |

The tier sets which command roles a hull can support; it does not automatically appoint an officer. A tier is not a shared feature list: cruisers and carriers can both be high-tier without using identical hull-class rules.

## Carrier pilot pool

Each carrier tracks its basic NPC pilots as a **finite numerical resource**, not as individual collectible cards. Its fighters and vessels draw from the same pool. Assigning a basic NPC uses one available pilot from the carrier; an internal ID used to track a deployment does not give that pilot a persistent card or bind them to a hull. Named personal wingman cards remain separate from the generic count. Each NPC deployment needs one ready pilot and one ready, launchable hull. A pilot already deployed or recovering cannot be assigned again. The number of NPC hulls that can launch is bounded by whichever count is lower: ready pilots or ready launchable hulls. Carrier stock, pilots, and losses do not transfer between Pegasus, Bifrost, and future carriers simply because they share a class.

The formation picker displays `Basic NPC - (N left)`, using ready pilots from the current carrier and subtracting basic bots already placed in the player's plan. Removing a planned bot restores one to the displayed count; planning alone is not a shared reservation. Real deployments use one shared pool for player formations and carrier self-defense. A pilot lost in battle is unavailable under the existing recovery rules. At zero ready pilots, no new basic bots can launch for either purpose until at least one returns, recovers, or is replenished. This does not recall bots already deployed.

**Implementation status:** The shared battle dispatcher already uses a limited carrier roster for NPC fighters. Carrier-supplied vessel deployment is a design rule for the future, not live functionality. Other Pegasus-specific flight flows still need to move onto the common carrier implementation.

## Wingman cards and assigned fighters

Any available pilot can fly any fighter or vessel, including a Civilian Freighter. There is no hull-specific pilot requirement or permanent pilot-to-ship bond. Pilot and hull readiness are tracked separately: if a pilot dies or a card is permanently removed, clear that pilot's assignment without deleting or transferring the hull. If the hull survived, it can be assigned to another ready pilot; if the hull needs repairs, it must be repaired before it can launch again. The player chooses the replacement rather than the game silently swapping pilots.

A formation pad pairs a **pilot card** with a separate **fighter or vessel hull**. Players will be able to own **Bot Pilot Cards**. Each card represents a unique bot pilot, separate from the carrier’s basic NPC pilot count. Card pilots use the same basic flight and wingman AI as ordinary bots, but are persistent characters, not disposable or interchangeable units. A downed card is handled by the separate revival rules below, not by spending another basic NPC to replace that character. For each formation slot, choose either one basic NPC from the carrier's pool or one ready Bot Pilot Card you own. A Bot Pilot Card fills the pilot requirement without using any of the carrier's basic NPC count. It can fly an eligible fighter or vessel, including a permitted carrier-owned hull, without changing who owns the ship or the card. A card cannot be used in two active slots or sorties at once. Destroying a hull does not erase its pilot's identity. A destroyed hull can be repaired. A downed **Bot Pilot Card** must be revived; if it is not revived before the applicable deadline, it dies and is removed. The exact deadline, revival cost, and acquisition rules are not yet specified. Do not apply permanent card loss to the carrier's generic NPC pool, which uses the existing roster recovery rules.

The current carrier picker only supplies a basic NPC option. Pegasus and Bifrost use the same local picker and Wing Two launch logic with independent saved pad assignments and their own Rift-3 readiness. Boarding from the four-pad hangar is solo. Boarding from the formation hall keeps the pilot in that hall until cockpit entry; the Battle Fleet Map starts the pilot docked on the carrier’s own exterior launch deck. An assigned, ready wingman follows the pilot’s takeoff in supported private flight modes. The picker is not a personal-card inventory or a revival system. Its availability check is a snapshot, not a launch reservation or a persistent stock write. Decorative parked ships do not represent usable inventory. Leena and Tomas are unique named NPC pilots represented by Bot Pilot Cards, not anonymous units in the basic NPC headcount. They remain Pegasus-affiliated but are reserved as the player's named wingmen, not available for autonomous Pegasus sorties, carrier defense, automatic replacements, or other generic roster use. They deploy only when the player selects them in a supported wingman flow or a mission explicitly assigns them as the player's wingmen. The reservation does not grant ownership of either card. Future card ownership and acquisition are separate from being assigned to fly alongside the player.

## Pegasus logistics reserve

Admiral Bishop's carrier owns five unarmed Civilian Freighters. These are not player inventory and do not contribute weapon power. Their intended use is logistics and future freighter missions. A Pegasus member may request one as a formation escort by pairing it with any available pilot on the same finite carrier roster. Ownership does not transfer. Players own only the hulls they acquired and brought; assigning a carrier-owned wingman does not add it to their inventory. A reserve vessel may not be issued twice or deployed without a ready pilot. The Solo Free Flight loaner is separate and does not reserve a real hull. Pegasus crew may use these internal ships for supported Pegasus missions without gaining ownership. Persistent formation borrowing and mission eligibility still need to be implemented.

### Formation borrowing: implementation design

1. Bind a crew's carrier membership to its authenticated pilot ID on the server. A visit or a docking receipt alone does not grant access to a carrier's stock. The current home-company choice is local profile data, so this membership check is still missing.
2. Save one independent **pilot + hull** pair per selected pad, up to eight escort pads around the player's front-middle lead. Do not reserve anything just by editing the plan. The picker should offer available pilots from the carrier pool and intact hulls from its own stock, including Swift-2, Bison-2 and Pegasus's five unarmed Civilian Freighters when flight support exists.
3. On a supported mission or formation launch, the server checks membership, mission eligibility, enough available basic NPCs, any distinct selected personal cards, and the requested hull quantities. Reserve the entire group against the same availability used by online sorties in one compare-and-swap transaction; if a pilot or hull has been taken since selection, return the conflict and let the player adjust. Never silently replace an unavailable card or fabricate a hull.
4. Start with the player's selected ship on the original deck of the carrier. In formation, the player lifts off first, then up to three wingmen stage at a time, leaving a random recovery pad open. An eight-wing group uses three waves (3 + 3 + 2). Freighters join formation and fly logistic objectives but never fire. Keep a stable class-appropriate fit for the actual hull rather than spawning every assignment as a Rift-3.
5. Return surviving pairs to the carrier and settle losses exactly once. Release abandoned reservations without minting hulls, and do not grant a mission reward or write a permanent loss from an unverified test session. Existing NPC recovery and future personal-card revival remain distinct. Private sessions need a trusted outcome path before consuming shared reserve resources; the current local wingman path is only a readiness snapshot.

## Manpower

Both current carriers use one scoring function and the same carrier-class launchable-hull list. The Galaxy Map's headline is launch-ready NPC reserve weapon power times ready NPC pilots. Swift-2 and Bison-2 are stored reserves, but are excluded until the shared battle dispatcher can launch them. Personnel without a launchable reserve airframe do not create power. Resolute is listed in the formation, but its guns are not part of this reserve-fighter metric. The existing inventory-only API score remains as a legacy field. Human readiness and fitted player weapons are not currently verified and should not be estimated from parked ownership rows.

The class rules added here cover the manpower calculation. Other carrier systems still contain vessel-specific wiring and require migration and tests before a third carrier is plug-and-play.

## Port resupply

Meridian Resupply is the first service port. Pegasus and Bifrost make independent scheduled visits. The clock starts when the carrier is stationary at the station; the first five minutes never restock anything. The current five-minute service scheduler may take up to five further minutes, so the ship stays in port for ten minutes. The scheduled service then replenishes the carrier's basic NPC roster and Rift-3 reserves to their normal caps for free, once per visit. Deployed NPCs remain leased, and the service does not add credits, repair personal ships, revive Bot Pilot Cards, or overwrite stock already above the normal cap. Attached ships travel with their carrier; independent multicrew resupply requires their own navigation and inventory.
